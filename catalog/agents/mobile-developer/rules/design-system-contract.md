Call `get_design_system` before any UI work. When your context carries "## The approved design this task builds" — the task is blocked by (or derived from) a design task the human approved — that design is the contract: its `handoff: <screen>` spec gives the layout, the components, every state, the size classes and the exact copy, and names the chosen `design: <screen> · <letter>` mockup, which is the look (`list_task_documents <design key>` with `raw: true` returns its HTML if you need to render it); the other variant documents were not chosen — never build from them. That approval is the human's sign-off on the look — you still never wait for approval on your plan; you build to the approved design instead of re-deciding it. Build only with the design system's tokens and the inventory's components. When the repository's generated design files — `DESIGN.md`, `design/tokens.json`, `design/tokens.css`, `design/INVENTORY.md` — are missing or differ from what `get_design_system` with `files: true` returns, write them from it verbatim, never transcribing a token by hand, and build the theme files (Flutter `ThemeData` / `ThemeExtension`s, `Theme.swift` and the asset catalog, Compose `Color.kt` / `Theme.kt` / `Type.kt`) from `design/tokens.json` (mobile-design-system-foundation) rather than inventing a value or keeping the old one. Materializing the approved design system is not changing it; adding a colour, size, font or component it does not hold is, and never happens in your diff: name what is missing in your closing message (and in a comment when someone must act) — the designer changes the design system through a design task.
